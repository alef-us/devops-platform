## Что особенно хорошо

### 1. Нет ненужного усложнения приложения

Для DevOps-проекта маленький Todo API — разумный выбор: он позволяет сосредоточиться на доставке и эксплуатации, а не на сложной бизнес-логике.

Разделение на endpoints, контракт хранилища и реализацию достаточно простое. Здесь **не нужны микросервисы, CQRS или дополнительные архитектурные слои ради портфолио**.

### 2. Есть аккуратность в деталях, а не только работающий happy path

В [хранилище](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/src/DevopsPlatform.Api/Todos/InMemoryTodoStore.cs):
- обновление сделано через `TryUpdate` с повторной проверкой, а не небезопасное «прочитать и перезаписать»;
- обновление не должно восстанавливать уже удалённую запись;
- сохраняются ID и время создания;
- порядок выдачи детерминирован;
- время передаётся через `TimeProvider`, что облегчает тестирование.

Для небольшого учебного приложения это хороший инженерный уровень.

### 3. Тесты проверяют реальное HTTP-поведение

[Integration-тесты](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/tests/DevopsPlatform.Api.Tests/ApiTests.cs) проверяют полный CRUD-цикл, `Location`, нормализацию заголовка, ошибки валидации и отсутствующие записи. Это существенно полезнее, чем тестировать исключительно методы, замокав всё вокруг.

### 4. CI — реально работающий контроль качества

В [workflow](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/.github/workflows/ci.yml) есть форматирование, строгая сборка, тесты, артефакты, ограничение времени и отмена устаревших запусков. Права по умолчанию ограничены `contents: read`.

Особенно хорошо, что после major-обновлений тестовых зависимостей **тесты действительно продолжают обнаруживаться, а покрытие — собираться**: это подтверждается логами, не только зелёным значком.

### 5. В roadmap уже есть проверки реального результата

Удачные критерии:
- запуск контейнера и HTTP smoke test;
- развёртывание в kind с проверкой через Service;
- проверка, что Prometheus действительно собирает метрики.

Это правильный подход: **проверять поведение, а не просто наличие Dockerfile, Helm chart или YAML**.

## Что плохо или пока недостаточно

### 1. Главный архитектурный риск — данные при переходе в Kubernetes

Сейчас каждый процесс держит собственный словарь:

- после перезапуска данные исчезают;
- две реплики имеют разные наборы задач;
- POST в одну реплику и GET через другую могут дать `404`;
- rolling update уничтожает состояние заменяемого процесса.

**Для текущего демо это допустимое ограничение, но для будущего масштабируемого CRUD-сервиса — уже проблема.** В [задаче Kubernetes](https://github.com/alef-us/devops-platform/issues/3) есть «HPA-ready», но подготовленность Deployment к HPA не делает само приложение корректным при нескольких репликах.

Перед этим этапом нужно явно выбрать:
- демонстрационное приложение с непостоянными данными и документированными ограничениями;
- либо общее устойчивое хранилище.

Не стоит добавлять PostgreSQL автоматически — сначала определить, что проект должен демонстрировать.

### 2. Readiness пока ничего не проверяет

В [точке входа](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/src/DevopsPlatform.Api/Program.cs) проверка `todo-store` всегда возвращает `Healthy`.

Для in-memory реализации это объяснимо. Но описание «dependencies are usable» сейчас сильнее фактического поведения.

При появлении БД необходимо:
- проверять её доступность с ограничением времени;
- возвращать неготовность при отказе;
- оставить liveness независимой от БД, чтобы её сбой не вызывал бессмысленные перезапуски приложения.

### 3. Высокое покрытие не означает достаточную проверку отказов

Не хватает сценариев:
- невалидный `PUT`;
- граничные длины заголовка: 200 и 201;
- повреждённый JSON и неподходящий тип содержимого;
- контракт Problem Details для ошибок;
- исключение хранилища и ответ `500`;
- конкурентные update/delete;
- поведение Production-конфигурации.

Отдельная деталь: в [тестах хранилища](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/tests/DevopsPlatform.Api.Tests/InMemoryTodoStoreTests.cs) `StepClock` изменяет общее поле без синхронизации, а используется в том числе из параллельного теста. Проверку количества записей это не обесценивает, но для проверки временных инвариантов такой fake ненадёжен.

### 4. Покрытие измеряется, но не является обязательным порогом

CI формирует отчёт, однако не ограничивает допустимое падение покрытия. Кроме того, публикация summary использует `|| true`, поэтому ошибка именно этого шага может остаться незаметной.

Лучше добавить:
- проверку, что обнаружены тесты и создан непустой отчёт;
- согласованный порог или контроль регрессии покрытия;
- явную ошибку при невозможности опубликовать ожидаемый результат.

**Не нужно добиваться 100% ради числа:** сейчас полезнее закрыть сценарии отказов.

### 5. Воспроизводимость сборки частичная

В [настройке SDK](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/global.json) разрешён `latestFeature`; Actions используют теги, runner — `ubuntu-latest`; NuGet lock-файлов нет.

Это удобный выбор для старта, не ошибка. Но при переходе к релизам стоит определить политику:
- фиксировать Actions на commit SHA;
- использовать locked restore;
- фиксировать образы по digest;
- обновлять зависимости контролируемыми PR.

### 6. Документация немного опережает результат

Начало [README](https://github.com/alef-us/devops-platform/blob/8dbe73a1ca60a220068d7da0b7fd94214281b208/README.md) звучит как описание уже существующей цепочки до monitored Kubernetes deployment, хотя roadmap честно показывает обратное.

Стоит сразу написать: **«Текущий статус: API + CI; остальные этапы в разработке»**, добавить ограничения хранения и примеры запросов. Схему текущей архитектуры тоже лучше показать сейчас, а не откладывать до последнего этапа.

## Что улучшать в следующих подходах

Я бы сохранил последовательность roadmap, но усилил критерии готовности.

| Итерация | Что сделать | Чем доказать готовность |
|---|---|---|
| **1. Укрепить основу** | Определить требования к данным; добавить негативные тесты и контроль результатов тестирования | CI обнаруживает тесты, проверяет ошибки и фиксирует ограничения приложения |
| **2. Контейнер** | Multi-stage, non-root, `.dockerignore`, сканирование; immutable image identity | Собранный образ запускается, выполняет CRUD и корректно завершается по SIGTERM |
| **3. Kubernetes** | Helm, ресурсы, probes, graceful shutdown; выбранная модель хранения | Проверки через Service, перезапуск Pod, rolling update; две реплики — если поддерживаются |
| **4. Наблюдаемость** | Метрики трафика, ошибок, задержек; dashboard; хотя бы один полезный alert | Искусственно вызвать отказ и увидеть метрику, alert и связанные логи |
| **5. Azure / Terraform** | OIDC, remote state, разделение plan/apply, подтверждение платных операций | Воспроизводимые создание и удаление стенда, контроль стоимости и оставшихся ресурсов |
| **6. Доставка** | Продвижение одного проверенного образа, проверка после деплоя, rollback | Развернуть плохую версию, обнаружить проблему и восстановить рабочую |

Для публичного развёртывания отдельно определить модель доступа: анонимный демо-CRUD или API с аутентификацией, лимитами и ограничением объёма данных.

### Главная рекомендация по процессу

**Каждый следующий PR должен отвечать на три вопроса:**
1. Какое поведение добавлено?
2. Как автоматически доказано, что оно работает?
3. Что происходит при отказе и как восстановиться?

Итог: **фундамент качественный, явных поломок базового CRUD я не обнаружил.** Самое ценное сейчас — не расширять список технологий, а довести один сценарий до конца: изменение → проверенный образ → развёртывание → наблюдаемый отказ → восстановление. Именно это превратит репозиторий из хорошего API с CI в убедительный DevOps-проект.
